# Vajrion — Secure FIR, Case & Digital Evidence Management

Vajrion is a full-stack React + Express application for FIR registration, case management, investigation evidence, case sharing, court proceedings, notifications and an Admin-only tamper-evident audit ledger.

## Production architecture

- **Frontend:** React + Vite, built to `frontend/dist`.
- **Backend:** Express 5 exposed through `api/index.js` for Vercel Functions.
- **Database:** PostgreSQL. The backend accepts `DATABASE_URL`, `POSTGRES_URL`, `POSTGRES_URL_NON_POOLING`, or `POSTGRES_PRISMA_URL`.
- **Evidence:** encrypted AES-256-GCM binary data stored in PostgreSQL `BYTEA`, with SHA-256 integrity hashes.
- **Authentication:** JWT + bcrypt password hashing.
- **Security:** Helmet, CORS, validation with Zod, login/signup rate limiting and role-based access control.

The production build does **not** use `better-sqlite3` and does not require a local SQLite database.

## Local development

Use Node.js 22.

```bash
cp .env.example .env
# Put a real PostgreSQL URL in DATABASE_URL and set JWT_SECRET/EVIDENCE_ENCRYPTION_KEY.
npm install
npm run seed
npm run build
npm start
```

For the frontend in a second terminal:

```bash
npm --workspace frontend run dev
```

The Vite development server proxies `/api` to `http://localhost:4000`.

## Database initialization and demo data

The backend creates the required PostgreSQL tables automatically on startup. To seed the demo accounts and sample case data:

```bash
npm run seed
```

To clear the application tables:

```bash
npm run reset
```

Demo credentials are printed by `npm run seed`. The seeded officer accounts are verified so they can sign in immediately; accounts created later by Admin start pending verification.

## Migrating the old SQLite data

The old SQLite file is intentionally **not** included in the production ZIP. To migrate an existing database, keep a copy of the original `securedocs_v2.db` outside the deployment and run:

```bash
SQLITE_SOURCE=/path/to/securedocs_v2.db npm --workspace backend run migrate:sqlite
```

The migration imports all application tables and resets PostgreSQL identity sequences. After migration, verify the audit ledger from the Admin UI/API. A legacy database can contain historical audit entries generated by the old hashing implementation; those entries are preserved as-is rather than silently rewriting history.

## Vercel deployment

1. Create a PostgreSQL database through a Vercel Marketplace Postgres provider such as Neon, Supabase or another supported provider.
2. Import this repository/ZIP into a Git repository and create a Vercel project with the repository root set to the `v10` directory.
3. Vercel will use the included `vercel.json`; no custom frontend build directory is required.
4. In **Vercel → Project → Settings → Environment Variables**, configure:
   - `DATABASE_URL` (or the Postgres URL automatically supplied by your storage integration)
   - `JWT_SECRET`
   - `EVIDENCE_ENCRYPTION_KEY`
   - `FRONTEND_ORIGIN` set to your deployed Vercel origin if you also plan to call the API from another frontend origin; for the bundled same-domain frontend, the default is sufficient.
   - `MAX_UPLOAD_MB=3.5` unless you deliberately change the upload architecture.
5. Deploy. The backend initializes the PostgreSQL schema during cold start.
6. Open `/api/health` on the deployed domain. It should return JSON with `status: "ok"`.
7. Run `npm run seed` against the production database only when you intentionally want the demo dataset.

### Important Vercel upload limit

Vercel documents a 4.5 MB limit for function request payloads. Vajrion therefore defaults evidence uploads to 3.5 MB so a multipart request stays below that platform limit. For larger evidence files, move file storage to an object-storage/direct-upload design instead of increasing the serverless request limit.
